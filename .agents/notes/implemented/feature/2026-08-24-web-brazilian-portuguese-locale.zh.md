# Agent Note: Web 巴西葡萄牙语语言选项

Status: implemented

[English](2026-08-24-web-brazilian-portuguese-locale.md) | 中文

## 问题

Web 客户端此前只提供 `zh` 与 `en` 两种语言，「设置」中的语言行只能在这两者之间选择。巴西葡萄牙语是产品尚未覆盖的最大开发者群体之一：使用 `pt-BR` 的浏览器会落入 `en` 回退，语言菜单也没有葡萄牙语可选项。

## 决策

把巴西葡萄牙语作为第三种语言引入，使用主语言子标签 id `pt`，`<html lang>` 解析为 BCP 47 标签 `pt-BR`——这与既有的 `zh` → `zh-CN` 安排一致，因为 locale id 是应用自己的词汇，而文档属性需要完整标签。语言行将其标注为 `Português (Brasil)`。

字典完整性契约原样扩展：`LocaleId` 变为 `'zh' | 'en' | 'pt'`，类型化 `register(ns, { zh, en, pt })` 重载以及每个包里的 `satisfies Record<Key, string>` 校验，使缺少或多余的 `pt` 键成为编译错误。全部 27 个客户端 locale 命名空间现在都带有 `pt` 词典；回退链（当前语言 → `en` → 键）与 `FALLBACK_LOCALE = 'en'` 保持不变，任何语言缺失的键仍解析到英文而非中文。浏览器检测无需改代码：`detectBrowserLocale` 已按主语言子标签匹配，因此 `pt-BR` 会落到 `pt`。

文案遵循一条规则：自然的巴西葡萄牙语，`{placeholder}` 占位符原样保留，产品名词（`Full access`、`plan mode`、`Session`、`API key`）与英文侧一致不翻译。欢迎声明文案与目录选择器对话框词典这些在类型化逐包词典之外注册的内容，也补充了 `pt` 条目。

## 备选方案

**使用独立的 `pt-BR` id。** 因对称性被否：应用的 id 是主语言子标签，且既有 `zh` 已经证明「id → 完整文档标签」的映射应属于 `DOCUMENT_LANGUAGE`，而不是 id 本身。

**巴西与欧洲葡萄牙语同时引入。** 因超出范围被否。需求是巴西葡萄牙语；欧洲变体以后可以随时加入，无需改动机制——注册表没有任何方言相关逻辑。

**未类型化注册保留 `en` 回退。** 与其他每个命名空间都提供全部语言的理由相同而被否：解析到 `pt` 的浏览器不应看到混合语言的界面，回退服务于真正的缺失，而不是跳过的词典。

## 测试

`locale.client.spec.ts` 固定三个自述标签，浏览器检测场景现在断言 `pt-BR` 解析为 `pt`；`apply.client.spec.ts` 断言 `pt` 席位已占用、语言行镜像全部三个 id。各包自带的词典测试（若有）扩展到 `pt` 词典，其余由既有 `test:gui` 套件覆盖。`settings-chrome` 的 e2e golden 不变：胶囊按钮只渲染当前语言的自身名称，因此 `zh`／`en` golden 不会出现第三个条目。

## 后果

**今后每个词典都需提供三种语言。** `LocaleId` 联合类型在编译期强制这一点；只注册 `zh`／`en` 的新包无法构建。成本有界：键集合都很小，且 `en` 侧自然是译者最顺手的来源。

**葡萄牙语用户的浏览器解析结果已改变。** 使用 `pt-BR`（或 `pt` 前缀）的浏览器在无存储偏好时会直接以葡萄牙语启动，此前会落到 `en`。`fr-FR` 的 e2e 场景仍覆盖「未提供语言」路径。

**标签不是 id。** `pt` 持久化在 `locale.preference` 并随设置文档流转；显示标签 `Português (Brasil)` 只是呈现。重命名标签不会触及任何已存储的值。
